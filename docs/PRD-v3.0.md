## 0. 现状盘点（实测结论，不是假设）

| 层面 | 现状 | 对本次需求的影响 |
| --- | --- | --- |
| 路由 | `/`、`/age/[range]`、`/quick`、`/quick/[slug]`、`/milestones`、`/sources`、`404` | 需新增 3 类路由：`/outdoor`、`/outdoor/[slug]`、`/about` |
| 导航 | `src/lib/url.ts` 的 `NAV` 常量 4 项：首页 / 快速查询 / 发育里程碑 / 来源与声明 | 扩到 5～6 项后 375px 会挤，必须给出移动端方案（见 2.2） |
| 内容模型 | `src/content.config.ts` 定义 3 个集合：`developmental`、`acute`、`milestones`（zod + Content Layer） | 户外数据**必须新建独立集合**，不能塞进 `developmental`（分类枚举、月龄主轴、来源结构都不兼容） |

| 搜索 | `scripts/postbuild.mjs` 生成 `search-index.json`；`GlobalSearch.astro` 的 `Item.type` 是 `'acute' \| 'developmental'`，`hrefOf()` 只拼两种链接，急症结果固定置顶 | 索引、类型联合、链接拼装、结果徽章、置顶逻辑都要同步改 |
| sitemap | `postbuild.mjs` 手写 URL 列表，只覆盖现有 4 类页面 | 新增路由需进 sitemap，且必须带 `/BabyCare` base 前缀 |
| 布局 | `BaseLayout.astro` 统一页头/页脚；页脚含全站免责声明 + **硬编码**「最后更新：2026-10-30」 | 关于页沿用同一布局；顺手把硬编码日期改为构建期注入，否则新功能上线后页脚仍在说 10 月 |
| 首页 | `index.astro` 48–72 行是 hero（出生日期 + 成长轴），118 行起是急症模块，141 行起是「还想看」卡片区 | 户外入口放「还想看」区和 hero 的 `link-row` 即可，**不得挤占急症入口首屏位置**（v2.0 硬约束） |
| 样式 | 原生 CSS + 设计令牌（`--paper` / `--brand` / `--warn` 等，2747 行），系统字体、零外部请求 | 新页面复用令牌；任何第三方地图 SDK / 字体 / 统计脚本都会破坏「零外部请求」架构前提 |
| 部署 | `.github/workflows/deploy.yml`：校验 → 构建 → 部署；`withBase()` 统一处理 `/BabyCare` 前缀 | 所有新链接必须走 `withBase()`，`verify:base` 需覆盖新路由 |

**核心判断**：这次不是「加两个页面」，而是**给站点引入第二类内容**。v2.0 的全部内容都是医学指南整理（可溯源、保守表达、逐字照录、医学复核）；户外场所是**会过期的本地实用信息**（票价、开放时间、预约规则）。两者的治理逻辑不同，必须在信息架构、视觉、文案、校验规则上显式分舱，否则会稀释站点最值钱的资产——可信度。

## 1. 本次目标与定位判断

### 1.1 三个模块的一句话定义

| 模块 | 定义 | 用户得到的价值 |
| --- | --- | --- |
| A 户外活动 | 北京地区**带 0～3 岁孩子可去**的户外场所清单，每条可核验、标注亲子设施与风险，并回链到站内安全知识 | 「周末去哪儿」+「出门前该注意什么」一次解决 |
| B 关于页 | 说明这个站是谁做的、内容怎么来的、怎么复核、怎么处理隐私、怎么纠错、未来要做什么 | 让读者知道**为什么可以信**、信到什么程度、怎么参与 |
| C 请作者喝杯咖啡 | 放在关于页末尾的低调自愿支持入口，静态二维码，不涉及在线支付 | 给维护者一点正反馈，不破坏公益属性 |

### 1.2 定位决策（需要作者拍板的第一件事）

**推荐：把户外活动做成「按月龄养育知识的日常生活延伸」，而不是一个独立的北京玩乐导航站。**

理由：站点已有 `sun-mosquito`（防晒防蚊）、`playground-safety`（游乐场安全）、`road-safety`（交通安全）以及烫伤 / 误吞 / 脱水 / 头部外伤等急症条目。户外场所详情页若按风险标签自动带出这些条目，新模块就与原有医学体系形成闭环，而不是一个挂在外面的口袋。

**内容分舱规则（写进页面，不只写进文档）**：

| | 知识区（现有） | 生活区（新增） |
| --- | --- | --- |
| 依据 | 国家卫健委 / WHO / AAP 指南，逐字照录关键征象 | 官方公园公告、市园林绿化局 / 市公园管理中心页面 |
| 复核 | 医学背景复核人 | 作者按季度实地/官网核验 |
| 时效 | 指南版本级 | **核验日期级**，超期必须标注或下线 |
| 措辞 | 分诊而非诊断，不给药品剂量 | 「设施适配」而非「发育建议」，不给医疗结论 |
| 视觉 | 现有分类色 / 警示色 | 新增一组「户外」中性色徽章，与红色急症警示、绿色医学色明确区分 |

## 3. 模块 A：户外活动（北京）

### 3.1 用户场景

| 编号 | 场景 | 真实问题 | 产品应答 | 成功判据 |
| --- | --- | --- | --- | --- |
| S4 周末 | 周六上午，想带 10 个月的孩子出门，不想开车太远 | 「附近有没有推车能走、有遮阴、不用预约的地方？」 | `/outdoor` 按区 + 推车友好 + 免费筛选 | 3 次交互内看到可用卡片 |
| S5 出门前 | 已经定了去某个有湖的公园 | 「水边要盯什么？中暑/蚊虫怎么办？」 | 详情页「出门前 3 分钟」清单，按风险标签回链 `/quick` 与 `/age` 条目 | 每类风险都有对应站内条目，无死角 |
| S6 核验 | 看到一张卡片写着免票 | 「这是不是今年的政策？」 | 卡片与详情页都显示核验日期 + 官方链接 + 「以官方公告为准」 | 100% 条目可见核验信息 |

**反场景**：不为「全市公园大全」「亲子餐厅打卡」「实时人流/天气/余票」优化（见第 10 章）。

### 3.2 内容范围

- **地理范围**：北京 16 区，首批不追求全覆盖，建议覆盖 ≥6 个区、12～18 个场所。
- **收录标准**（必须同时满足）：① 户外为主或有明确户外活动区域；② 0～3 岁孩子可进入；③ 有可公开核验的官方信息源；④ 免费或低门槛公共空间优先，商业场所单列并明确标注。
- **暂不收录**：纯室内场馆、需要复杂预约且规则频繁变动的场馆、距离市区过远且无公共交通的山野路线、涉及水域且无护栏的野点。
- **候选清单见附录 B**，全部只是名称候选，**任何票价、开放时间、设施信息都必须核验后写入**。

### 3.3 数据模型（新集合 `outdoor`）

路径建议 `src/content/outdoor/<slug>.md`（区放 frontmatter，不建 16 层目录，降低维护成本）；loader 用 `glob()`，schema 用 zod，与现有集合写法一致。

| 字段 | 类型 | 必填 | 规则 / 用途 |
| --- | --- | --- | --- |
| `title` | string | ✅ | 官方名称，2～24 字，不用简称做标题 |
| `district` | enum | ✅ | 16 区中文名枚举，不允许「近郊」「城北」等模糊值 |
| `venue_type` | enum | ✅ | `city_park` / `forest_park` / `wetland` / `riverside` / `botanical` / `zoo` / `playground` / `scenic` / `commercial` |
| `summary` | string | ✅ | 20～80 字，只描述「这地方什么样」，不写推荐语、不写医疗建议 |
| `tags` | string[] | ✅ | 1～6 个，如 `大草坪` `湖边` `可推车` `有儿童区` |
| `age_fit` | enum[] | ✅ | 复用 7 个 `AGE_RANGES`，或 `all`；表示**设施适配**，不是发育建议 |
| `stroller` | enum | ✅ | `yes` / `partial` / `no` / `unknown`（`unknown` 也要能显示，不许猜） |
| `shade` / `nursing_room` / `toilet` / `playground` | enum | ✅ | 同上四态；页面渲染为「有 / 部分 / 无 / 未核实」 |
| `water_hazard` | boolean | ✅ | 有开放水域即 `true`，触发安全联动规则 O-06 |
| `free` | boolean | ✅ | 是否免门票（不含停车、游乐项目） |
| `ticket_note` | string | — | 收费说明；**页面统一附加**「以官方公告为准」，不由作者手写 |
| `open_hours` / `reservation` | string | — | 开放时间 / 预约要求，同上 |
| `address` / `transit` / `parking` | string | ✅ / — / — | 地址必填；交通与停车可选，禁止编造 |
| `official_name` / `official_url` | string / url | ✅ | 官方信息源名称与 https 链接，域名需在 allowlist 登记 |
| `seasons` | enum[] | — | `spring`/`summer`/`autumn`/`winter`，静态季节标签，**不接实时天气** |
| `safety_tags` | enum[] | ✅ | `water` / `sun` / `mosquito` / `traffic` / `fall` / `choking` / `crowd`；驱动详情页安全清单 |
| `related_dev` | string[] | — | 关联 `developmental` 条目 slug，校验存在性（O-09） |
| `related_acute` | string[] | — | 关联 `acute` 条目 slug；可由 `safety_tags` 自动补默认集合 |
| `verified_on` | date | ✅ | 官方信息核验日期，页面显著位置显示 |
| `last_reviewed` / `reviewer` | date / string | ✅ | 沿用 v2.0 的复核字段习惯 |
| `draft` | boolean | — | 默认 false；`true` 不进列表、索引、sitemap |
| `lng` / `lat` / `coord_system` | number / number / enum | — | **MVP 不启用**，仅 L1/L2 地图方案才写入，坐标系显式标注 |

**明确不设的字段**：`rating`（评分）、`distance`（距离）、`likes`、任何 UGC / 打卡 / 评论字段。

### 3.4 构建期校验规则（新增 O 组，接入 `validate-content.mjs`）

| 编号 | 规则 | 级别 |
| --- | --- | --- |
| O-01 | `slug` 全局唯一、小写连字符，与文件名一致 | 构建失败 |
| O-02 | `district` 属于 16 区枚举 | 构建失败 |
| O-03 | `official_name` + `official_url` 非空，https，域名在 allowlist | 构建失败 |
| O-04 | `verified_on` 存在且 ≤ 今天；> 180 天输出警告（页面打「待复核」角标），> 365 天构建失败 | 警告 / 失败 |
| O-05 | 页面渲染层统一为所有票价 / 时间 / 预约字段追加「以官方公告为准」，禁止作者在正文里自写免责话术造成遗漏 | 构建失败（模板断言） |
| O-06 | `water_hazard: true` 或含 `water` 标签时，`related_acute` 必须覆盖对应急症条目 | 构建失败 |
| O-07 | 全站扫描：户外条目正文不得出现药品名与剂量（沿用急症硬约束） | 构建失败 |
| O-08 | 禁止医学化断言词表：「促进发育」「最适合 X 月龄」「有助于长高」「治疗」等 | 构建失败 |
| O-09 | `related_dev` / `related_acute` 的 slug 必须真实存在 | 构建失败 |
| O-10 | `draft: true` 不进入列表页、搜索索引、sitemap | 构建失败 |
| O-11 | `stroller` 等四态字段不允许留空，未核实必须显式 `unknown` | 构建失败 |
| O-12 | 户外条目**不参与月龄主轴**：不得被 `monthlyTasks.ts` 引用、不得出现在首页「本月 3 件事」 | 构建失败 |

### 3.5 列表页 `/outdoor` 规格

1. **页头**：标题「北京亲子户外」+ 副标题明确「本页为本地生活信息整理，非医疗建议，信息会过期」+ 全库最近核验日期 + 收录数量。
2. **筛选维度**：区（16 区，默认全部）、场所类型、月龄适配、免费 / 收费、推车友好、**避开水域**（安全向反选）。多选组合，提供「重置」。
3. **排序**：默认按区 + 名称；不提供「离我最近」，不做定位。
4. **卡片**：名称、区 / 类型徽章、一句话、设施图标行（推车 / 遮阴 / 母婴室 / 水域提示）、核验日期（`2026-11 核验` 或 `待复核`）、官方链接图标（外链 `rel="noopener noreferrer"`，新窗口并带明确标识）。
5. **交互**：优先复用 `/quick` 页已有的轻量客户端筛选模式（≤3KB JS）；**JS 关闭时必须能看到全部条目**，筛选控件用原生 `details` / 表单降级。
6. **空态**：写明「该组合暂无收录」+ 推荐场所的 GitHub Issues 链接（带模板参数），不显示空白页。
7. **免责**：全站页脚之外，本页顶部二次说明「场所信息以官方公告为准，出行前请再核对」。

### 3.6 详情页 `/outdoor/[slug]` 规格

自上而下固定顺序：面包屑 → 标题 + 区 / 类型 / 核验状态 → 一句话概览 → **带娃适配表**（四态字段 + 月龄适配）→ **实用信息**（地址、开放时间、票务、预约、公共交通、停车、官方链接、复制地址）→ **出门前 3 分钟**（由 `safety_tags` 生成的安全清单，逐条回链 `/quick/[slug]` / `/age/[range]`）→ **这个月龄的相关提醒**（`related_dev`）→ **来源与核验**（官方源名称、链接、核验日期、复核人）→ **纠错入口** → 页脚免责。

**铁律**：安全清单只给「注意什么 + 站内哪里看」，不自行写处置步骤、不写药品名与剂量；一旦涉及急症处理，一律跳转到 `/quick` 对应条目。

### 3.7 地图与位置服务（合规硬约束，必须先决策）

这是本模块最大的架构分叉，按三档给出，**推荐 L0**：

| 档 | 做法 | 依赖 | 适配性 |
| --- | --- | --- | --- |
| **L0（推荐 MVP）** | 只给「地址文本 + 复制地址按钮 + 官方链接」，不做地图、不存坐标 | 零依赖、零第三方请求 | ✅ 与现有「零外部请求 / 零追踪」架构完全一致 |
| L1 | 「在地图中打开」外链，用合规平台的官方 URI / 网页搜索链接（按官方文档确认是否需 key；若需 key 则退回 L0） | 外链，用户主动点击才发起请求 | 可接受，需标注外链 |
| L2（二期，可选） | 页面内嵌地图 + 多点标记 | 需地图 SDK、key、域名白名单、配额 | ⚠️ 与静态站架构冲突，需单独评审 |

**L2 若未来要做，必须遵守**：

- 仅允许**腾讯地图（默认）、高德、百度、天地图**；禁止 Google Maps / Apple Maps / Bing 海外版 / Mapbox / Leaflet+OSM 等境外或无资质底图。
- WorkBuddy 本地代理模式（`_TMapSecurityConfig` + `__WB_HTTP_PORT__` 占位符）**只在本地运行时有效**，GitHub Pages 上的公网静态页无法使用，因此 L2 必须由作者自行申请平台 key。key 明文放前端会被抓取，须配置 Referer 域名白名单与配额；商业场景应走后端代理（但本项目不引入后端，故 L2 仅限个人自用）。
- 坐标系标注：腾讯 / 高德 GCJ-02，百度 BD-09，天地图 CGCS2000；不得混用。
- 不采集、不存储、不公开用户位置；不做「按距离排序」、不做定位授权（个人信息保护要求，也符合站点零追踪承诺）。
- 不标注军事管理区、涉密单位、未公开敏感坐标；批量点位只使用公开场所公开地址。

### 3.8 时效治理与纠错

- 每个条目有 `verified_on`，页面显示；超过 180 天自动打「待复核」角标，超过 365 天构建失败（强制下线或重新核验）。
- 建议作者按季度做一次批量核验；`README` 增加「新增 / 更新一条户外场所」的操作步骤。
- 纠错入口统一指向 GitHub Issues（需作者提供仓库 Issues 模板），不留邮箱也能闭环；页面不设评论、不设表单后端。
- 官方链接失效检测：纳入现有 `verify` 的人工走查清单（不自动抓取，避免构建期网络依赖）。

### 3.9 与现有内容的双向关联（本模块的差异化价值）

## 附录 C：为什么推荐「不做地图」

1. 现有站点是纯静态、零外部请求、零追踪，页头搜索都是构建期索引 + 按需加载 fuse.js；地图 SDK 会一次性引入第三方脚本、瓦片请求与配额依赖，是架构级别的倒退。
2. GitHub Pages 没有后端，无法安全托管 key；前端明文 key 只能靠 Referer 白名单兜底，属于个人项目可接受的边界，但不应在 MVP 就背上。
3. 位置服务必须只用合规底图（腾讯 / 高德 / 百度 / 天地图），且不得采集用户位置；L0 方案完全绕开这些约束，却仍能满足「知道地方在哪、怎么去」的核心需求。
4. 若后续作者确认要 L2，按第 3.7 节单独评审，不影响 M1～M4 的交付。

## 附录 D：v3.0 实施记录（2026-11-12）

本次实际落地与原需求构造的差异，以下为最终口径：

| 项 | 原设计 | 实际落地 | 原因 |
| --- | --- | --- | --- |
| `free` 字段 | boolean | 三态 `free / paid / unknown` | boolean 无法表达「未核实」，会逼作者猜 |
| 关系字段 | `related_dev` + `related_acute` 两套 | 统一为 `relations: [{ type, slug }]`，旧 `related` 仍兼容 | 避免两套字段各说各话；反向边由构建期补全 |
| 派生层 | 排到 v3.5 | v3.0 最小化落地：`dist/derived/` 下的关系图、复核状态、词表、站点导览四份 JSON | 户外回链、搜索同义词、关于页导览已经依赖它，推迟会返工 |
| 第二索引轴 | 抽象描述 | 落地为 `/scene/[slug]` 六个场景页 + 首页场景入口 | 主题是纵向时间线，场景是横向「此刻入口」 |
| 咖啡二维码 | 需作者提供 | 页面已就绪，构建期检测 `public/images/coffee-*.png`，放入即显示 | 不伪造二维码；没有素材时显示上传说明 |
| 户外数据 | 12～18 条 | 10 条：9 个市属公园 + 奥林匹克森林公园 | 只收能确认官方入口的场所；未核实字段一律 `unknown`，不编造价票与开放时间 |
| 复核状态 | 只写在字段里 | `/sources` 与户外详情页显示复核状态；`reviewer` 为「作者待核验」 | 公开状态比统一填「内容组」更可信 |

**验收结果**：`validate` / `verify` / `verify:base` 全绿；37 个页面；搜索索引 18.6KB（预算 60KB）；关系边 80 条；户外 10 条全部有官方来源与核验日期。
