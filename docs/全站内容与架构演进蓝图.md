## 1. 先给结论：五条判断

1. **这个站真正的资产不是 41 条内容，是那套内容纪律**：zod schema + 构建期业务校验 + 逐字照录 + 不写药品剂量 + 急症独立于月龄主轴。所有扩展都应该放大这套纪律，而不是绕开它。市面上育儿内容比这多一百倍的站多得是，能证明「每条从哪来、谁复核过、什么时候复核」的极少。
2. **当前最大的瓶颈不是内容少，是只有一条半主轴**：月龄是唯一主轴，急症是一条旁路，搜索是唯一横向入口。家长的真实提问却至少是五维的——症状、场景、时间点、物品/环境、此刻该做什么。缺的是**第二索引轴**，不是再写 20 条卡片。
3. **条目之间其实没有关系网**：`related` 字段 34 条里 14 条非空，17 个引用全部指向急症条目、0 个指向另一条知识条目；PRD 5.4 的校验规则也只检查「指向 acute 的 slug 存在」。所以「知识图谱」目前不存在，跨月龄主题（睡眠、辅食、安全、口腔）被切在 7 个格子里互不相连。
4. **先修地基，再堆内容**。如果现在直接补到 100 条，得到的会是 100 张互不相连的孤卡，而且维护成本线性上涨。优先级应当是：**关系与索引 > 补条目 > 新页面 > 新交互**。
5. **有一个候选被低估了：离线 PWA**。v2.0 第 18 章把它放在「v3 候选池」最后，但主画像是「凌晨 2 点、手机、慌乱、弱网」，急症页离线可打开的价值高于补任何一条知识。我建议把它提到 v3.5 的第一位。

## 3. 三个结构性局限

### 3.1 单轴模型把连续主题切碎了

「睡眠」在 7 个阶段各有一条：新生儿睡多久 → 昼夜颠倒 → 睡眠倒退 → 分离焦虑夜醒 → 并觉 → 换床 → 睡前程序与夜惊。它们讲的其实是同一条时间线，但页面上彼此看不到对方，读者只能靠自己一页页翻。辅食、安全、口腔、情绪同理。

**后果**：站点擅长回答「5 个月该注意什么」，不擅长回答「我家孩子睡眠一直有问题，从头到尾该看哪些」。后者才是家长真实的提问方式。

### 3.2 「关系」目前只是字段，不是能力

`related` 只用于阶段页底部展示几个急症入口，没有反向、没有类型、没有构建期完整性检查（除了存在性）。户外模块、关于页、主题页要互相回链，靠手写 slug 会迅速失控。

### 3.3 检索层太薄，接不住口语

`search-index.json` 只有 `slug / title / tags / summary / type / category / age_range`，fuse.js 加 `includes` 兜底。家长不会搜「胃食管反流」「特应性皮炎」「睡眠倒退」，他们会搜「吐奶」「红屁股」「睡不踏实」「一到晚上就哭」。现有 130 个标签是作者写给机器看的，不是家长嘴里的话。

## 4. 目标架构：加一层「派生层」

这是我最想提的一条。**不新增运行时依赖、不引入后端**，只在构建期多算一步：

```text
内容层（不变）          条目 .md / .yaml + frontmatter
   ↓ 构建期读取
派生层（新增，核心）    词表、关系图、主题索引、场景索引、同义词表、
                       复核状态、变更记录、离线预缓存清单 → 静态 JSON
   ↓ 页面消费
呈现层（少量新增）      现有 7 类页面 + 主题页 / 场景页 / 清单页
```

**为什么是这一层**：

- 关系、反链、词表、同义词、引用次数、影响范围，全部可以在 `npm run build` 时算完，运行时零开销，完全符合静态站约束。
- 页面由派生数据生成，主题页不用手写内容；新增一条 `.md` 会自动出现在所有相关聚合页里。
- 派生层可以带 `version`，配合 CHANGELOG 做「哪次构建改了什么」。
- 户外模块、关于页的「站点导览」、来源页的「引用计数」本质都是派生层的消费者，一次建好，三处受益。

**派生 JSON 草案**（`dist/derived/*.json`，不进页面 HTML）：

| 文件 | 内容 | 消费者 |
| --- | --- | --- |
| `taxonomy.json` | 受控词表：`topic`（睡眠/喂养/安全/皮肤/口腔/情绪/发育/出行）× `synonyms`（口语→规范词） | 搜索、主题页、场景页 |
| `relations.json` | 双向关系图：`from / to / type(related_acute, same_topic, next_stage, checklist, outdoor)` | 详情页「接着看」、阶段页、户外页 |
| `topics.json` | 每个主题下按时间线排列的条目 slug | `/topic/[slug]` |
| `scenes.json` | 场景→条目/急症/清单的映射（夜醒、吐奶、出门、体检前） | `/scene/[slug]`、首页第二入口 |
| `review-status.json` | 每条的复核人、复核日期、距今天数、状态 | `/sources`、页脚「内容新鲜度」 |
| `changelog.json` | 按构建版本聚合的新增/修改/下线条目 | `/sources`、关于页更新日志 |
| `precache.json` | 离线预缓存清单（全部急症页 + CSS + 索引） | Service Worker |

**配套的两条硬规则**：① 关系一律**双向自动生成**，作者只在源条目写一次；② 任何 slug 引用在构建期校验存在性，悬空即失败（现有规则 7 已覆盖 acute，扩到全类型即可）。

## 5. 内容体系：按「问题密度」重排，不按分类配额

### 5.1 明显的内容缺口（按优先级，不含任何诊断/用药内容）

| 组 | 主题 | 理由 | 风险 |
| --- | --- | --- | --- |
| **A 高频低风险，建议先补** | 哭闹与安抚、吐奶/溢奶、大小便与便秘、尿布疹与皮肤护理、发热的家庭观察与**何时就医**、维生素 D 等补充剂的「遵医嘱」表述、回应性照护与亲子互动、儿保体检节点（带什么、问什么） | 0～12 个月最常被搜索、现有 34 条几乎没覆盖；都能靠「观察 + 就医时机 + 官方来源」写清楚 | 低，但仍需明确边界 |
| **B 结构性新类型** | 家庭安全清单（按月龄）、出门/待产清单、安全座椅核对、拍嗝/洗澡/剪指甲/口腔清洁的「怎么做」 | 这些是**任务型内容**，不是知识卡片，现有 `developmental` 的 5 分类装不下 | 低，需要新集合 |
| **C 需复核人到位才动** | 任何涉及症状判断、阈值、处置步骤的内容 | 一旦写错就是医疗风险 | 高 |
| **D 明确不补** | 疾病百科、用药与剂量、生长曲线自测、个体化喂养处方、发育「训练」方案、中医偏方、商业产品推荐 | v2.0 第 18 章已划界，不松动 | — |

### 5.2 建议新增的三种内容类型（比补条目更重要）

| 类型 | 结构 | 呈现 | 举例 |
| --- | --- | --- | --- |
| `checklist` | 一组可勾选项 + 适用月龄 + 来源；勾选状态只存 `localStorage` | 清单页，打印友好 | 「会翻身之后的家庭安全 12 项」 |
| `timeline` | 节点 + 该节点该做什么 + 官方链接，不写补种规则、不做提醒 | 时间线页 | 「0～3 岁儿保与疫苗节点对照」 |
| `procedure` | 分步操作 + 常见错误 + 何时停下来就医 | 操作卡 | 「拍嗝」「安全座椅安装核对」 |

三者共同约束：**不写入任何个体化数值、不做「是否达标」的判断、不给药品与剂量**。这正是 v2.0「分诊而非诊断」原则在新内容类型上的延伸。

### 5.3 每条新内容的上线门禁（把纪律变成流程）

1. 能指回原文的哪一份、哪一章节？（`source.section` 或 `source.url`）
2. 有没有越界到诊断、用药、个体化建议？
3. 谁复核的、什么时候？（`reviewer` / `last_reviewed`，且复核人要能对应到真实角色）
4. 会不会过期？（会 → 进 `outdoor` 那套核验日期机制；不会 → 进年度复查）
5. 归哪个主题、和哪些条目相连？（由派生层生成，不手写）

### 5.4 顺手要修的两处一致性

- **来源承诺**：要么把首页 / 页脚 / README 的「NHC、WHO 与 AAP」改成如实表述，要么真的补上 AAP / WHO 条目并把 `/sources` 的版本表做全。我倾向前者先做（改一句话），后者排期。**对外宣称的依据必须等于站内实际引用的依据**，这是可信度站点的底线。
- **复核人**：`reviewer: "内容组"` 全站统一、41 条同一天复核，等于没记录。建议 `/sources` 显式写清「本站点由谁整理、急症分级经谁核对、哪些内容尚待医学复核」，把状态公开，比 pretending 全部已复核更可信，也更符合 PRD 13.4 的初衷。

## 7. 检索层：把「家长的话」翻译成站内的词

现有 `scenario_tags` 是给机器填的近义词，建议新增一张**受控同义词表**（`src/content/data/synonyms.yaml`，构建期并入 `taxonomy.json`），只做映射、不做判断：

| 家长可能输入 | 映射到 | 落到 |
| --- | --- | --- |
| 吐奶、溢奶、喷奶 | `feeding.spitup` | 相关阶段条目 + 「何时就医」急症 |
| 红屁股、尿布疹 | `skin.diaper` | 皮肤护理条目 |
| 睡不踏实、一放下就醒、落地醒 | `sleep.night_waking` | 睡眠时间线主题页 |
| 一到晚上就哭、黄昏闹 | `crying` | 哭闹与安抚条目 |
| 不吃奶、厌奶、奶量下降 | `feeding.intake` | 「怎么判断吃够了」 |
| 便秘、几天不拉、大便干 | `stool` | 大小便条目 |
| 长牙、流口水、咬东西 | `teething` | 出牙期条目 |

规则：同义词表**只影响检索与跳转，不产生任何新结论**；表中词条需人工维护、不自动抓取；索引体积继续守 v2.0 的 60KB 预算。明确不做语义向量、不做 AI 问答、不做「根据描述判断可能是什么」。

## 8. 内容治理：把 PRD 里写过的机制真正落地

PRD 13 章定义了状态机、五条铁律、更新 SLA、复核人要求，但代码里目前只实现了 `last_reviewed` 时效警告。建议补四件小事：

1. **状态机落地**：`draft → reviewed → verified`，`status` 进 schema；`verified` 必须有真实 `reviewer`；未 `verified` 的急症条目在页面上标注「待医学复核」。
2. **CHANGELOG 构建期生成**：对比上次构建的条目摘要，自动列出新增/修改/下线，页面可查（PRD 13.3 已经在要求它）。
3. **影响范围分析**：某份指南发布新版时，构建期能一键列出「引用了这份指南的全部条目」，让 30 天响应 SLA 可执行。
4. **过期自动降级**：PRD 13.2 第 5 条「超过 12 个月自动降为 draft」目前只是 warning，建议改为真正的状态变更 + 页面角标。

## 9. 对 v2.0「v3 候选池」的逐项裁决

这是上一版明确留到 v3 讨论的四项，我的建议：

| 候选 | 裁决 | 理由 |
| --- | --- | --- |
| **离线 PWA** | ✅ **提到最前，v3.5 首位** | 纯静态、零追踪、零后端，与所有约束兼容；直接服务 S1「凌晨 2 点弱网看急症」。做法：`manifest.webmanifest` + Service Worker，构建期生成 `precache.json`，预缓存全部 `/quick/*` 急症页 + CSS + 搜索索引；scope 用 `/BabyCare/`；cache 版本与 CHANGELOG 联动；不申请通知权限、不做推送、不缓存任何外部资源 |
| **疫苗接种时间表** | ⚠️ **改造后做**：只做「官方免疫程序节点对照表」，链接到现行国家免疫规划疫苗儿童免疫程序及说明；不写补种规则、不做个性化排程、不做提醒（v2.0 明令不做提醒） | 属 `timeline` 类型，价值高，但必须由最新官方文件逐字核对，且同样要过复核门禁 |
| **按月龄的喂养日程表** | ❌ **仍不做** | 极易被读成「掐表喂」的处方，与站内「按需哺乳、不掐表」直接冲突，个体化风险高于价值。替代方案：做「喂养信号与常见困惑」主题页 |
| **生长曲线可视化** | ❌ **仍不做** | 需要连续录入测量值并做百分位判断，属于个体化评估；本地存储一组儿童生长数据也放大隐私责任。v2.0 的判断是对的 |

## 10. 路线图：三个版本，先地基后内容

## 11. 优先级原则与「仍然不做」

**排序原则**：能放大内容纪律的 > 能降低维护成本的 > 能覆盖更多提问方式的 > 单纯增加条目数的 > 增加交互复杂度的。

**仍然不做**（继承 v2.0 第 18 章，并补三条）：用户系统与多宝宝档案、云端同步、AI 问答与症状自查问卷、生长曲线与百分位、用药与剂量、疫苗提醒、社区/评论/投稿、多语言、**按距离/定位的个性化推荐**、**实时数据（天气/人流/余票）**、**任何第三方统计或埋点 SDK**。

## 附录 B：派生层 `relations.json` 条目形状（示意）

```json
{
  "from": "developmental/fall-prevention",
  "to": "acute/head-injury",
  "type": "related_acute",
  "bidirectional": true,
  "generated": true,
  "source": "frontmatter.related"
}
```

`type` 建议枚举：`related_acute` / `same_topic` / `next_stage` / `checklist` / `outdoor` / `timeline`。作者只写在源条目，反向边由构建期补全；任一边悬空即构建失败。
